10.000 Zeilen rendern, ohne den Browser einzufrieren

Große Tabellen bringen die Oberfläche in die Knie, wenn wir versuchen, alles auf einmal zu zeichnen. Sehen Sie, wie Virtualisierung, Intersection Observer und native Web Components selbst bei riesigen Listen 60 fps halten.

Magdalena Kaltenbach Frontend-Entwicklerin · pura 22. Mai 2026 · 8 Min. Lesezeit Performance Web Components DOM

Sie haben wahrscheinlich schon erlebt, wie eine Tabelle mit Tausenden Datensätzen eine flüssige Seite in eine Diashow verwandelt. Selten ist das Framework schuld: Es ist der Browser, der versucht, Zehntausende DOM-Knoten zu erstellen, das Layout zu berechnen und alles in einem einzigen Frame zu zeichnen. In diesem Artikel zerlegen wir das Problem in Teile und lösen jeden davon mit Werkzeugen, die bereits zur Plattform gehören.

Das Problem des riesigen DOM

Jede Zelle, die in den Baum gelangt, kostet Speicher und Layout-Zeit. Mit 10.000 Zeilen und sechs Spalten sind das 60.000 Knoten allein in der Tabelle. Der Browser muss sie alle messen, positionieren und zeichnen, sogar die außerhalb des Bildschirms. Der Nutzer zahlt diesen Preis mit Rucklern.

Die goldene Regel: Das DOM sollte nur enthalten, was das Auge sehen kann. Alles unterhalb des sichtbaren Bereichs ist Verschwendung, bis es zu einem Pixel wird.

Listen-Virtualisierung

Die Kernidee ist, nur das sichtbare Fenster plus ein paar zusätzliche Zeilen Puffer zu rendern. Während das Scrollen voranschreitet, recyceln wir dieselben Knoten und aktualisieren ihren Inhalt, statt neue Elemente zu erzeugen. Ein Platzhalter legt die Gesamthöhe fest, damit die Bildlaufleiste genau bleibt.

Das sichtbare Fenster berechnen

Bei fester Zeilenhöhe ist die Rechnung einfach: Der erste sichtbare Index ist der Scroll-Versatz geteilt durch die Zeilenhöhe.

const ROW_H = 36; // feste Höhe jeder Zeile (px) const OVERSCAN = 6; // zusätzliche Zeilen oben/unten function visibleRange(scrollTop, viewportH, total) { const start = Math.max(0, Math.floor(scrollTop / ROW_H) - OVERSCAN); const count = Math.ceil(viewportH / ROW_H) + OVERSCAN * 2; const end = Math.min(total, start + count); return { start, end }; }

Die Knoten recyceln

Statt Zeilen zu entfernen und neu zu erstellen, behalten wir einen festen Pool und verschieben jede mit transform: translateY(). Transforms lösen kein Reflow aus, nur Compositing, sodass das Scrollen flüssig bleibt.

  • Verwenden Sie die Knoten wieder, zerstören Sie sie nicht in jedem Frame.
  • Nutzen Sie translateY statt top, um sie zu positionieren.
  • Aktualisieren Sie den Inhalt über textContent und vermeiden Sie innerHTML.

IntersectionObserver und Scroll-Spy

Um auf das zu reagieren, was den Bildschirm betritt und verlässt, ohne jedes Scroll-Ereignis abzuhören, ist IntersectionObserver das richtige Werkzeug. Er plant die Callbacks außerhalb des kritischen Scroll-Threads. Die <pura-scroll-spy>-Komponente in diesem Artikel nutzt genau diese API, um den Index-Eintrag rechts hervorzuheben.

const io = new IntersectionObserver((entries) => { for (const e of entries) { if (e.isIntersecting) e.target.dataset.seen = "true"; } }, { rootMargin: "0px 0px -65% 0px" }); document.querySelectorAll("[data-row]").forEach((el) => io.observe(el));

Wirklich messen

Optimierung ohne Messung ist Rätselraten. Öffnen Sie vor und nach jeder Änderung das Performance-Panel und betrachten Sie die langen Frames. Das Ziel ist einfach: Kein Frame darf 16,6 ms überschreiten.

  1. Zeichnen Sie ein Profil auf, während Sie die Liste bis ganz nach unten scrollen.
  2. Identifizieren Sie die langen Aufgaben, die rot markiert sind.
  3. Bestätigen Sie, dass Layout und Paint nach der Virtualisierung geschrumpft sind.

Fazit

Riesige Listen müssen nicht langsam sein. Rendern Sie nur das Sichtbare, recyceln Sie Knoten, delegieren Sie die Sichtbarkeitserkennung an IntersectionObserver und messen Sie jeden Schritt. Die Plattform liefert bereits alles, was Sie brauchen, ohne schwere Abhängigkeiten.
