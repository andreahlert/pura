Afficher 10 000 lignes sans figer le navigateur

Les grandes tables mettent l'interface à genoux lorsqu'on tente de tout peindre d'un seul coup. Découvrez comment la virtualisation, les intersection observers et les Web Components natifs maintiennent 60 fps même avec des listes massives.

Margaux Caldéron Ingénieure front-end · pura 22 mai 2026 · 8 min de lecture Performance Web Components DOM

Vous avez sans doute déjà vu une table de milliers d'enregistrements transformer une page fluide en diaporama. Le framework est rarement en cause : c'est le navigateur qui tente de construire des dizaines de milliers de nœuds DOM, de calculer la mise en page et de tout peindre en une seule frame. Dans cet article, nous allons décomposer le problème et résoudre chaque partie avec des outils déjà fournis par la plateforme.

Le problème du DOM géant

Chaque cellule qui entre dans l'arbre coûte de la mémoire et du temps de mise en page. Avec 10 000 lignes et six colonnes, cela fait 60 000 nœuds rien que dans la table. Le navigateur doit tous les mesurer, les positionner et les peindre, même ceux hors écran. L'utilisateur paie ce coût en saccades.

La règle d'or : le DOM ne doit contenir que ce que l'œil peut voir. Tout ce qui se trouve sous la ligne de flottaison est du gaspillage jusqu'au moment où cela devient un pixel.

La virtualisation des listes

L'idée centrale est de n'afficher que la fenêtre visible plus quelques lignes de marge. À mesure que le défilement avance, on recycle les mêmes nœuds et on met à jour leur contenu au lieu de créer de nouveaux éléments. Un espaceur définit la hauteur totale pour que la barre de défilement reste précise.

Calculer la fenêtre visible

Avec une hauteur de ligne fixe, le calcul est simple : le premier indice visible est le décalage de défilement divisé par la hauteur de ligne.

const ROW_H = 36; // hauteur fixe de chaque ligne (px) const OVERSCAN = 6; // lignes supplémentaires au-dessus/en dessous function visibleRange(scrollTop, viewportH, total) { const start = Math.max(0, Math.floor(scrollTop / ROW_H) - OVERSCAN); const count = Math.ceil(viewportH / ROW_H) + OVERSCAN * 2; const end = Math.min(total, start + count); return { start, end }; }

Recycler les nœuds

Au lieu de supprimer et de recréer les lignes, on conserve un pool fixe et on déplace chacune avec transform: translateY(). Les transforms ne déclenchent pas de reflow, seulement du compositing, donc le défilement reste fluide.

  • Réutilisez les nœuds, ne les détruisez pas à chaque frame.
  • Utilisez translateY plutôt que top pour les positionner.
  • Mettez à jour le contenu via textContent, en évitant innerHTML.

IntersectionObserver et scroll-spy

Pour réagir à ce qui entre et sort de l'écran sans écouter chaque événement de défilement, IntersectionObserver est le bon outil. Il planifie les callbacks en dehors du thread critique de défilement. Le composant <pura-scroll-spy> de cet article utilise justement cette API pour mettre en évidence l'élément d'index à droite.

const io = new IntersectionObserver((entries) => { for (const e of entries) { if (e.isIntersecting) e.target.dataset.seen = "true"; } }, { rootMargin: "0px 0px -65% 0px" }); document.querySelectorAll("[data-row]").forEach((el) => io.observe(el));

Mesurer pour de vrai

Optimiser sans mesurer, c'est deviner. Avant et après chaque changement, ouvrez le panneau Performance et observez les frames longues. L'objectif est simple : aucune frame ne doit dépasser 16,6 ms.

  1. Enregistrez un profil en faisant défiler la liste jusqu'en bas.
  2. Repérez les tâches longues signalées en rouge.
  3. Vérifiez que la mise en page et le rendu ont diminué après la virtualisation.

Conclusion

Les listes énormes n'ont pas à être lentes. N'affichez que ce qui est visible, recyclez les nœuds, déléguez la détection de visibilité à IntersectionObserver et mesurez chaque étape. La plateforme fournit déjà tout ce dont vous avez besoin, sans dépendances lourdes.
