Renderizzare 10.000 righe senza bloccare il browser

Le tabelle di grandi dimensioni mettono in ginocchio l'interfaccia quando proviamo a disegnare tutto in una volta. Scopri come la virtualizzazione, gli intersection observer e i Web Components nativi mantengono 60 fps anche con liste enormi.

Margherita Caldera Ingegnere front-end · pura 22 maggio 2026 · 8 min di lettura Prestazioni Web Components DOM

Probabilmente hai già visto una tabella con migliaia di record trasformare una pagina fluida in una presentazione di diapositive. Raramente la colpa è del framework: è il browser che cerca di costruire decine di migliaia di nodi del DOM, calcolare il layout e disegnare tutto in un singolo frame. In questo articolo scomporremo il problema in parti e risolveremo ciascuna con strumenti che la piattaforma offre già di serie.

Il problema del DOM gigante

Ogni cella che entra nell'albero costa memoria e tempo di layout. Con 10.000 righe e sei colonne, fanno 60.000 nodi solo nella tabella. Il browser deve misurarli, posizionarli e disegnarli tutti, anche quelli fuori dallo schermo. L'utente paga questo costo con gli scatti.

La regola d'oro: il DOM dovrebbe contenere solo ciò che l'occhio può vedere. Tutto ciò che sta sotto la piega è spreco fino al momento in cui diventa un pixel.

La virtualizzazione delle liste

L'idea centrale è renderizzare solo la finestra visibile più qualche riga extra di margine. Man mano che lo scorrimento avanza, ricicliamo gli stessi nodi e aggiorniamo il loro contenuto invece di creare nuovi elementi. Uno spaziatore imposta l'altezza totale affinché la barra di scorrimento resti precisa.

Calcolare la finestra visibile

Con un'altezza di riga fissa, il calcolo è semplice: il primo indice visibile è lo scostamento di scorrimento diviso per l'altezza della riga.

const ROW_H = 36; // altezza fissa di ogni riga (px) const OVERSCAN = 6; // righe extra sopra/sotto function visibleRange(scrollTop, viewportH, total) { const start = Math.max(0, Math.floor(scrollTop / ROW_H) - OVERSCAN); const count = Math.ceil(viewportH / ROW_H) + OVERSCAN * 2; const end = Math.min(total, start + count); return { start, end }; }

Riciclare i nodi

Invece di rimuovere e ricreare le righe, manteniamo un pool fisso e spostiamo ciascuna con transform: translateY(). I transform non innescano il reflow, solo il compositing, quindi lo scorrimento resta fluido.

  • Riutilizza i nodi, non distruggerli a ogni frame.
  • Usa translateY invece di top per posizionarli.
  • Aggiorna il contenuto tramite textContent, evitando innerHTML.

IntersectionObserver e scroll-spy

Per reagire a ciò che entra ed esce dallo schermo senza ascoltare ogni evento di scorrimento, IntersectionObserver è lo strumento giusto. Pianifica i callback al di fuori del thread critico di scorrimento. Lo stesso componente <pura-scroll-spy> di questo articolo usa proprio quell'API per evidenziare l'elemento dell'indice a destra.

const io = new IntersectionObserver((entries) => { for (const e of entries) { if (e.isIntersecting) e.target.dataset.seen = "true"; } }, { rootMargin: "0px 0px -65% 0px" }); document.querySelectorAll("[data-row]").forEach((el) => io.observe(el));

Misurare davvero

Ottimizzare senza misurare è tirare a indovinare. Prima e dopo ogni modifica, apri il pannello Performance e osserva i frame lunghi. L'obiettivo è semplice: nessun frame deve superare i 16,6 ms.

  1. Registra un profilo mentre scorri la lista fino in fondo.
  2. Individua le attività lunghe contrassegnate in rosso.
  3. Conferma che il layout e il rendering si sono ridotti dopo la virtualizzazione.

Conclusione

Le liste enormi non devono essere lente. Renderizza solo ciò che è visibile, ricicla i nodi, delega il rilevamento della visibilità a IntersectionObserver e misura ogni passaggio. La piattaforma offre già tutto ciò di cui hai bisogno, senza dipendenze pesanti.
